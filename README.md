# High-Coverage Outlier Representation in Low-Bit MX Formats for Efficient LLM Inference (ICCAD 2026)

**OMMX (Outlier-Managed-MX)** is a dual-resolution MX format: MXINT2 for the dense majority, MXFP4
for a high-coverage outlier region under a shared power-of-two scale. This repository is the **GPU
half** of the artifact: the accuracy evaluation and the serving kernels for vLLM and HF-eager. The
Nucleus NPU (paper §3.2, §4.3) is a separate codebase and is not included.

Our code is Apache-2.0. The vendored trees and their licences are listed in
[`THIRD_PARTY.md`](THIRD_PARTY.md). How each number was measured, and what it cannot show, is
documented next to the code that produced it (`figure/`, `ommx_gpu_serve/bench/`,
`ommx_gpu_serve/tests/`).

### How the arms were run

- **HF-eager** measures the KV kernel alone, in the framework KIVI and Kitty ship in; **vLLM**
  adds the engine (paged KV, CUDA graph). KIVI and Kitty have no vLLM integration.
- **KIVI CUDA** is built for sm_80 and sm_90; `ommx_gpu_serve/tests/test_kivi_gqa_equivalence.py` pins it
  against KIVI's own dequantization on both GPUs (a GPU test; it skips without the extension). Each KIVI cell is the faster of that kernel and
  KIVI's dequantize-and-dense path; the kernel won at every context (`figure/merge_kivi_paths.py`; both logs are kept beside
  the merged file, and `figure/collect.py` refuses a KIVI file whose own path record is not
  the kernel it is drawn as).
- **KIVI Triton** is referenced by upstream's model code only from a commented-out line and
  requires group size 64, so that arm packs the cache at 64 instead of the recipe's 32.
- **dtypes and versions**: KIVI and Kitty run fp16 on torch 2.4.1+cu121 with transformers 4.43.1
  and 4.53.2, as their code requires; the bf16 and OMMX arms run torch 2.11.0+cu130 with
  transformers 4.57.6. The bf16 HF arm uses a static cache with sdpa.
- **OMMX in vLLM** is configured from the engine's 128K maximum context, so every context runs
  the long-context rung and the tensor-core tile; 1K decodes slower than 4K (8.63 vs 6.99 ms)
  because the kernel takes a single KV split below 2K tokens. Block size 16 (32 is supported and
  verified; +26% at 4K).
- **vs bf16**: OMMX decode is still slower than bf16 (64K: 22.6 ms vs 14.3 Triton / 5.8
  FlashAttention). The win over bf16 is KV capacity, not speed.

## Setup

```bash
uv pip install -e 'ommx_gpu_serve[dev,bench]'   # the package, pytest, matplotlib (CPU)
uv pip install -e 'eval[ruler]'            # the lm-eval / RULER harness (optional)
python -m pytest ommx_gpu_serve/tests -q   # the GPU-only cases (kernel parity, packer, linear) skip without CUDA
```

The root `pyproject.toml` only declares the per-method dependency bundles (`.[ommx]`, `.[kivi]`,
`.[kitty]`); `./run.sh setup` prints the per-method virtualenv commands. The numbers above were
measured on torch 2.11.0+cu130 / transformers 4.57.6 (bf16 and OMMX arms) and torch 2.4.1+cu121
(KIVI, Kitty); `eval[ruler]` carries no upper pins, so a fresh install resolves newer versions.

The shipped panels regenerate from the raw logs without a GPU:

```bash
./run.sh figure --data-dir figure/data_h200_final --out-tag h200_20260905   # -> figure/fig_tpot_h200.png
./run.sh figure --data-dir figure/data_a100_w2   --out-tag a100_20260905   # -> figure/fig_tpot_a100.png
```

(`figure/data_h200/` and `figure/data_a100/` are earlier sweeps kept as evidence; their JSONs
are marked SUPERSEDED and refused. The linear-latency panels come from
`figure/data_{h200,a100}/linear_mem_bound.json` via `figure/plot_linear_tpot.py`.) The serving
paths need a CUDA GPU (sm_80 or sm_90), vLLM 0.21 with the TurboQuant KV-cache dtype, and
`meta-llama/Llama-3.1-8B-Instruct`, which is gated: accept its licence on Hugging Face and
download it before running with `HF_HUB_OFFLINE=1`. `./run.sh bench` drives the benches; KIVI
and Kitty need their own environments (`repro/README.md`), and `eval/lcb/` refers to a
checkout that is not in this repository.
